# 岗位真相与公司研究

把一份 JD 还原成容易理解、可核验的岗位研究报告；需要时继续连接用户的真实简历，形成岗位适配判断、能力迁移表达和面试引导话术。

## 模式选择

根据用户本轮意图选择模式：

1. **岗位解析模式**：用户只想看懂 JD、公司或岗位工作时，分析 JD 和公司，不读取简历。
2. **JD 与简历适配模式**：用户明确要求结合个人简历判断适配度、对齐经历、修改表达或准备面试话术时，读取当前工作区或附件中的简历，并完成岗位研究、证据映射和面试准备。

用户只提供 JD 且没有表达个人匹配意图时，保持岗位解析模式。用户在后续消息中补充个人匹配意图时，切换到 JD 与简历适配模式，并复用已经完成的岗位研究。

## 使用边界

- 每次处理一家公司和一个岗位。遇到多个岗位时，请用户指定本次目标。
- 读取用户提供的文本、网页、截图、图片或文件。图片需要先进行视觉检查并准确转录关键内容。
- 默认研究公开网页及用户提供的材料。
- 只提炼 JD 明确提出的岗位要求，不给 JD 句子计算 AI 概率、真实性分数或保留/删除标签。
- 岗位解析模式不读取候选人简历，不进行个人匹配。
- JD 与简历适配模式默认给出高、中、低等定性结论及分维度依据，不使用缺少标准支撑的单一百分比。用户明确要求量化时，先说明评分维度、权重和证据。
- 只使用简历、用户补充材料和已核验信息中的事实。将团队结果与个人贡献分开，将推测内容标记为“待确认”，禁止补造数字、所有权、技术实现和业务结果。
- 默认在对话中提供简历表达建议，不覆盖简历源文件。只有用户明确要求写入或修改文件时才执行文件编辑。

## 开始前

确认以下信息是否可获得：

1. 公司名称或官网。
2. 岗位名称。
3. JD 正文、岗位链接、截图或文件。

公司存在同名主体、品牌名和工商主体不一致等情况时，先核对官网、地点、产品或招聘主体。仅在歧义会显著改变研究结论时向用户提问。

使用 JD 与简历适配模式时，再确认简历来源：

1. 优先读取用户本轮指定或附加的简历。
2. 用户未指定时，在当前工作区查找文件名含“简历”、`resume` 或 `CV` 的 PDF、DOCX、Markdown、文本或图片文件。
3. 只有一份明显有效的简历时直接读取；存在多份且无法判断当前版本时，列出候选文件并请用户选择。
4. 找不到简历时，先完成可独立成立的岗位解析，再请用户提供简历后继续适配分析。

## 工作流程

### 1. 准确读取 JD

- 保留岗位名称、公司、地点、经验、学历、薪资等基础信息。
- 提取所有明确要求，合并完全重复的表达，保留数字、行业、客户、产品阶段、团队规模、技术和结果要求。
- 将职责中的动词、工作对象和结果连起来，例如：`澄清税务师事务所需求 → 转成工具调用与流程节点 → 交给研发 → 完成 UAT → 推动付费上线`。
- 避免把“沟通能力强”“结果导向”等通用表达写成岗位核心价值，除非 JD 给出了具体使用场景。

### 2. 判断岗位核心工作

综合 JD 的职责、量化目标、客户对象、产品阶段和公司业务，输出：

- 一句话岗位使命。
- 3—5 项核心工作。
- 需要交出的结果。
- 关键协作对象。
- 最难的工作环节。
- 判断依据。

岗位使命要回答“公司为什么要招这个人”。核心工作要回答“入职后主要把时间花在哪里”。当结论来自综合判断时，明确标记为“推断”。

### 3. 快速扫描整家公司

先了解公司整体，再深挖与岗位直接相关的业务线。执行实时网页搜索，优先寻找：

- 公司官网、产品页、解决方案、客户案例、价格或采购信息。
- 官方公众号、新闻稿、演示材料、产品文档和招聘页面。
- 工商、监管、招投标、应用商店、开发者平台等可核验材料。
- 可信媒体、行业媒体、数据库、招聘平台和访谈。
- 员工评价、论坛、社区讨论等弱信号。

按照 `references/research-method.md` 的方法判断来源、时效、冲突和信息缺口。

### 4. 讲清相关产品和商业模式

围绕 JD 对应业务回答六个问题：

1. 公司卖什么？
2. 谁实际使用？
3. 谁决定购买和付钱？
4. 客户为什么愿意买？
5. 公司怎样获得收入？
6. 这个岗位处于业务链条的哪个环节？

优先使用具体产品、客户和交易方式。公开资料缺少收费信息时，写明“公开资料未确认”，并把可能的收费方式标记为推断。

### 5. 整理证据和未知项

- 一个可信来源可以支撑一项事实；来源易得时可增加旁证。
- 关键事实后添加可点击链接。
- 区分“已确认事实”“推断”“待验证”。
- 多个来源互相冲突时，并列展示差异、日期和采信理由。
- 社区或匿名评价只能作为弱信号，禁止单独支撑公司产品、收入、客户规模等结论。
- 禁止用常识补齐融资、ARR、客户数、团队规模、收入占比和内部汇报关系。

### 6. 输出报告

读取 `references/report-template.md`，按模板生成约 2000—3500 字的中文报告。信息不足时缩短报告，禁止用通用行业知识填充篇幅。

默认先在对话中输出。只有用户明确要求保存时，才创建 Markdown 文件。

## JD 与简历适配模式工作流

完成岗位核心工作判断后，读取 `references/resume-match-template.md` 并执行以下步骤。

### 1. 建立简历事实表

- 按经历记录公司或项目、时间、角色、任务、动作、交付物、结果、指标、工具和协作对象。
- 标明每项事实的简历位置或来源，保留原始数字和责任范围。
- 将个人主导、个人参与、团队结果和个人方案分别记录，避免互相替换。
- 简历描述含糊时，标记“待确认”，不要自行补全。

### 2. 拆解岗位能力

- 将 JD 要求整理为硬条件、核心能力和加分能力。
- 把抽象要求还原为实际工作机制，例如将“AI 产品经验”拆成需求场景、方案设计、模型能力边界、评测验收和迭代推进。
- 判断每项要求在实际工作中的使用场景和交付结果，避免只比对关键词。

### 3. 做证据映射

逐项连接 `JD 能力 → 简历事实 → 匹配类型 → 可用表达 → 风险边界`：

- **直接匹配**：简历中存在同类场景、动作和交付结果。
- **可迁移能力**：行业或产品不同，但底层任务机制相同；明确说明共同机制和迁移边界。
- **真实缺口**：简历没有足够证据；给出补充材料、学习证明、作品 Case 或面试诚实回应方案。

优先寻找真实业务机制、决策过程和结果证据。关键词相同只能作为线索，不能单独证明适配。

### 4. 转成简历表达

- 用 `业务场景 + 个人动作 + 方法或机制 + 交付结果` 重写可迁移能力。
- 保留有意义的专业术语，删除与岗位无关的执行流水账。
- 对缺少数字或事实支撑的内容使用“待补充”或可替换占位，禁止把建议写成已经发生的经历。
- 同时给出“原能力如何对应岗位能力”的解释，让用户能够在面试中讲清迁移逻辑。

### 5. 生成带着面试官走的话术

使用候选人口吻，围绕用户最有证据的 2—3 个项目设计面试路径：

1. 一句话候选人定位，直接对齐岗位使命。
2. 60—90 秒自我介绍，主动放入 2—3 个可追问的事实钩子。
3. 为每个钩子准备 `一句话结论 + 2—3 个证据点 + 一个边界或复盘点`。
4. 提供从陌生行业、能力缺口或角色边界转回优势经历的自然承接句。
5. 预测 5—10 个业务型追问，并给出口语化、可记忆的参考回答。

引导面试的目标是让面试官沿着用户真实优势继续追问。每个钩子必须能够由简历或用户材料支撑，避免设计无法承接的故事。

## 写作要求

- 开头先给“3 分钟看懂岗位”。
- 每个模块先写一句大白话结论，再提供证据和细节。
- 使用短段落和清晰的小标题；每个列表保持 3—7 项。
- 专业术语确有必要时保留，并在首次出现时用一句通俗语言解释。
- 将“赋能、抓手、协同、闭环、端到端、生态”等词替换成具体动作和结果，技术术语或原始 JD 用词除外。
- 直接写清谁做什么、服务谁、交付什么、怎样衡量。
- 使用自然、克制的中文，兼顾专业性与阅读轻松度。
- 引用靠近所支持的事实，报告末尾再列精简来源清单。
- 简历适配部分保持候选人口吻，先给结论，再给证据和边界；避免把简历原句换词后重复一遍。

## 完成前检查

- 能否在 3 分钟内说清公司做什么、岗位做什么？
- 是否保留了 JD 中所有重要数字和硬要求？
- 岗位使命是否有 JD 或公司业务依据？
- 产品、使用者、付费方、购买原因和收入方式是否分别讲清？
- 是否把推断写成了事实？
- 是否标出公开资料不足和来源冲突？
- 是否生成 5—10 个能够验证真实职责的面试问题？
- 是否删除了空泛重复和难懂黑话？
- 进入简历适配模式时，是否找到了明确的简历来源并标出事实依据？
- 是否逐项区分直接匹配、可迁移能力和真实缺口？
- 简历建议和面试话术是否都能回到用户真实经历？
- 每个面试引导钩子是否准备了可承接的证据、边界和追问答案？
